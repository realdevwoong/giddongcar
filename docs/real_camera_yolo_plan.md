# 실물 Pinky Pro 카메라 인식·주행 기획 및 기술 검토

## 1. 목표와 범위

최종 목표는 `pinky_fleet` 관제 프로그램을 실행하면 실물 Pinky Pro의 카메라 영상이 로봇별 화면에 나타나고, 지도에서 목표 지점을 지정해 Nav2로 이동하는 동안 카메라 인식 결과도 주행 판단에 반영되는 것이다. 구현은 영상 표시, 인식 검증, Nav2와의 안전한 결합 순으로 진행한다.

이 문서는 실물 로봇만 다룬다. Gazebo·시뮬레이션 변경은 범위에서 제외한다. 두 로봇은 현재 운영 규칙대로 각각 ROS_DOMAIN_ID 15와 17을 사용한다.

## 2. 현재 확인된 자산과 상태

### `~/Desktop/yolo`

- `1_realtime.py`: 로컬 웹캠을 열어 `yolo11n.pt` 객체 탐지를 수행하고 결과 창을 표시한다.
- `realtime_seg.py`: 로컬 웹캠을 열어 `yolo11n-seg.pt` 세그멘테이션 결과를 표시한다. 해당 파일은 폴더 안에 없으므로 실행 전에 제공 또는 경로 수정이 필요하다.
- `yolo11n.pt`, `yolo26n.pt`: YOLO 일반 객체 탐지 가중치.
- `yolov8n-seg.pt`: 사전 학습된 세그멘테이션 가중치.
- 노트북 예제는 COCO 이미지의 사람·버스 등 일반 객체 세그멘테이션을 보여준다.

이 자산은 파이프라인 시제품을 만드는 데 쓸 수 있지만, 차선과 횡단보도를 바로 인식하는 모델이라고 볼 수는 없다. 도로 경계·주행 가능 영역·차선은 픽셀 단위 분할 또는 전용 차선 모델이 필요할 수 있다. 횡단보도도 목표 환경에서 직접 데이터와 라벨을 마련해 평가해야 한다. 실물 영상으로 학습·검증하기 전에는 인식 성능을 가정하지 않는다.

현재 구현은 관제 대시보드에서 BLE로 카메라 시작·중지를 요청하고, `http://<robot-ip>:5000/`의 HTTP MJPEG를 받아 웹 화면에 표시한다. YOLO 오버레이와 탐지 요약도 대시보드에 표시한다. 인식 결과는 아직 ROS 주행 명령에 연결하지 않는다. 카드의 **인식 관찰 시작**을 누르면 새 프레임에서 객체 종류/개수가 바뀔 때 관제 이벤트 기록에 남긴다. 이 기록은 브라우저 화면 메모리에서만 유지되며, 이동·정지·속도 명령을 보내지 않는다.

### ROS 저장소

- `docs/structure.md`는 센서 처리 패키지로 새 `pinky_camera`를, 직접 카메라 주행 로직으로는 별도 `pinky_driving`을 제안한다.
- `pinky_fleet`은 PC에서 로봇별 Nav2와 웹 대시보드를 운영한다. 실물 도메인은 15/17이다.
- 이번 변경 전 웹 대시보드는 지도·로봇 위치·Nav2 상태가 중심이었으며 카메라 입력/표시 기능이 없었다. 현재 브랜치에서 PC 측 영상 패널을 추가했다.
- `pinky_bringup`이 `cmd_vel`을 구독한다. 실물 문서에 따르면 명령이 끊겨도 마지막 속도로 계속 주행할 수 있으므로, 제어 노드 정지 시 0 속도를 보내는 동작이 필요하다.
- Nav2도 최종적으로 `cmd_vel`을 발행한다. Nav2와 비전 주행기가 동일 토픽에 동시에 발행하지 않도록 제어권을 하나로 중재해야 한다.
- IP·도메인·경로는 코드에 고정하지 않고 launch 인자나 파라미터로 전달한다. 카메라 처리는 제조사 패키지를 직접 수정하지 않는 것을 원칙으로 한다.

## 3. 권장 기술 구성

### 실행 위치

초기 구성은 **Pinky Studio로 로봇 카메라 스트림을 시작하고, 관제 PC에서 HTTP MJPEG 수신·추론·표시**로 한다. `pinky_fleet` launch는 관제 실행 시 대시보드 안의 카메라 수신 기능도 함께 시작한다. 이 구성은 로봇의 연산량을 낮추지만 WiFi 대역폭·지연·연결 안정성을 실측해야 한다.

향후 로봇에서 ROS 이미지 토픽을 제공하는 구성이 확인되면 입력부를 교체 또는 추가해도 인식 결과 인터페이스는 유지한다. 카메라 원본 스트림이 ROS에서 직접 제공되는지 여부는 현재 문서만으로 확정할 수 없다.

### 패키지 책임

| 구성 | 패키지 / 프로세스 | 책임 |
|---|---|---|
| 카메라 수신 | 현재 `pinky_fleet/pinky_fleet/camera_stream.py` | 로봇 스트림 연결, 재연결, 최신 프레임 관리, 입력 상태·지연 표시 |
| 일반 객체 오버레이 | 현재 `pinky_fleet/pinky_fleet/perception.py` | 선택된 모델로 프레임을 추론하고 오버레이·클래스·성능 상태 생성 |
| 전용 도로 인식 | 후속 별도 모듈/패키지 후보 `pinky_camera` | 학습 모델과 도로 정책이 확정되면 데이터·추론 계층을 분리 검토 |
| 관제 표시 | `pinky_fleet` | 로봇별 원본/오버레이 영상 및 연결·추론 상태 표시 |
| 주행 판단 연동 | `pinky_fleet`의 Nav2 연동 또는 별도 `pinky_driving` | Nav2 목표 주행 중 인식 정보를 이용한 감속·정지·목표/경로 관리 |
| 주행 명령 중재 | 별도 설계 컴포넌트 | Nav2와 보조 제어 명령의 단일 제어권, 안전 조건, 정지 감시 |
| 모터 구동 | 제조사 `pinky_bringup` | 기존 `cmd_vel` 구독 유지. 꼭 필요한 경우가 아니면 수정하지 않음 |

첫 구현은 `pinky_fleet` 프로세스가 로봇의 HTTP MJPEG 스트림을 받아 기존 대시보드의 같은 HTTP 주소로 전달하는 형태로 한다. 현재 웹 서버와 카메라 미리보기 자리가 이미 `pinky_fleet`에 있어 별도 영상 서버를 브라우저에 노출하지 않아도 된다. 카메라 입력·추론을 별도 ROS 노드나 `pinky_camera`로 분리하는 것은 ROS 토픽 입력이 필요해지거나 배포·연산 요구가 갈라질 때 검토한다.

### 데이터 흐름

```text
Pinky 카메라
    └─ Pinky Studio 활성화 HTTP MJPEG (`:5000/`, 로봇 이미지 v1.9+)
          ↓ WiFi
관제 PC: pinky_fleet
    ├─ 최신 프레임 수신 및 타임아웃 감시
    ├─ YOLO 추론
    ├─ 오버레이 영상
    └─ 인식 결과·신뢰도·입력 시각을 상태 API로 제공
          ↓ 같은 fleet HTTP 서버
      웹 관제: 로봇별 영상과 인식 상태 표시

후속 주행 단계:
지도 목표 → Nav2 경로 추종 → (카메라 인식 + 라이다 장애물) 주행 정책/안전 감독
                                      ↓
                            단일 cmd_vel 중재 → pinky_bringup
```

최종 동작은 카메라 노드가 Nav2와 나란히 `cmd_vel`을 발행하는 형태가 아니다. 관제에서 보낸 Nav2 목표를 유지하면서 인식 결과가 Nav2 속도 제한, 주행 일시정지/재개, 필요 시 목표 취소 또는 재계획 중 어떤 동작을 유발할지 정하고, 실제 명령은 충돌 없는 한 경로로 로봇에 전달한다.

## 4. ROS 인터페이스 초안

현재 구현은 로봇 HTTP MJPEG를 직접 받아 대시보드의 HTTP MJPEG 경로로 전달하므로 ROS 영상 토픽을 쓰지 않는다. 로봇 카메라가 ROS 이미지로 제공되거나 인식 노드를 분리할 때는 로봇별 DDS 도메인 15/17 안에서 아래 상대 토픽 초안을 쓸 수 있다. 실제 적용 전에는 영상 입력 방식과 QoS를 확인한다.

| 이름(상대 토픽) | 타입 후보 | 용도 |
|---|---|---|
| `camera/image_raw` | `sensor_msgs/msg/Image` | ROS 카메라 입력을 채택할 경우 원본 프레임 |
| `camera/image/compressed` | `sensor_msgs/msg/CompressedImage` | WiFi 전송 또는 대시보드 영상 입력 후보 |
| `perception/image` | `sensor_msgs/msg/Image` 또는 compressed | 탐지 결과 오버레이 |
| `perception/objects` | `vision_msgs/msg/Detection2DArray` | 객체 종류, 상자, 신뢰도, 헤더 시각 |
| `perception/road_mask` | `sensor_msgs/msg/Image` | 주행 가능 영역·차선 분할 결과(모델 확정 후) |
| `perception/status` | 진단 메시지 또는 간단한 상태 메시지 | 입력 신선도, 추론 FPS, 오류, 모델 식별자 |
| `cmd_vel` | `geometry_msgs/msg/Twist` | 주행 단계 이후 단일 제어 발행자만 사용 |

### 전송·시간 처리

- 원본 RGB 1280×720, 30 FPS라고 가정하면 비압축 영상 크기는 약 2.76 MB/frame, 약 663 Mbit/s(8비트 RGB·헤더 제외)다. 이는 문서에 설정된 Gazebo 카메라 규격을 기준으로 한 대역폭 예시이며, **실물 카메라 규격은 미확인**이다. WiFi로 원본 영상을 그대로 보내는 설계는 피하고 실제 해상도·FPS·압축률을 계측한다.
- 현재 입력은 로봇 HTTP MJPEG, 브라우저 전달은 대시보드 HTTP multipart JPEG다. ROS 이미지 입력을 추가할 경우 `image_transport` compressed 경로를 검토한다.
- 최신 프레임 우선(QoS depth 1 또는 이에 준하는 큐 정책)으로 오래된 프레임이 쌓이지 않게 한다. 추론이 밀리면 프레임을 건너뛴다.
- 각 인식 결과에 원본 프레임의 헤더 시각을 유지한다. 영상 시각이 오래됐거나 연결이 끊기면 상태를 stale/offline으로 바꾸고 후속 주행 정책은 정지로 취급한다.
- 로봇·PC 시계 동기화는 기존 `docs/real.md` 절차를 따른다. 노드 런치에서 도메인을 지정하고, 코드에는 IP·도메인을 박지 않는다.

## 5. 인식 전략

1. **일반 객체:** `yolo11n.pt`를 첫 비교 대상으로 삼아 사람·차량 등 COCO 클래스를 확인한다. `yolo26n.pt`는 패키지·버전 호환성 및 실제 지연 측정 전까지 후보 가중치다.
2. **주행 가능 영역·차선:** `yolov8n-seg.pt`는 일반 COCO 사전학습 모델이므로 차선/도로 경계 전용 결과를 기대하지 않는다. 초기에는 화면에 출력만 하고, 주행 환경(바닥 재질, 조명, 카메라 장착각)에 맞는 데이터 수집·라벨링 후 세그멘테이션 또는 전용 차선 모델을 비교한다.
3. **횡단보도:** 필요한 클래스·정책을 정의한 뒤 직접 촬영한 영상에서 라벨링한다. 단순 객체 박스 검출인지 노면 영역 분할인지 요구사항을 정하고, 오검출·미검출을 별도로 측정한다.
4. **장애물:** 카메라 검출은 의미 분류에 쓰고, 거리·충돌 회피는 기존 라이다/Nav2를 우선 사용한다. 카메라 2D 박스만으로 안전한 정지 거리를 추정하지 않는다. 깊이 센서가 없는 현재 구성에서는 크기 기반 거리 추정을 안전 기능으로 쓰지 않는다.
5. **속도 최적화:** 작은 모델부터 PC CPU/GPU에서 초당 프레임, 추론 지연, CPU/GPU 사용량을 실측한다. 목표 FPS는 실측 뒤 정한다. `imgsz`, 입력 FPS, 압축 품질을 조정하고 TensorRT/ONNX 등의 배포 최적화는 정확도 기준이 확보된 뒤 검토한다.

## 6. 최종 목표까지 필요한 작업 목록

아래 순서로 진행한다. 앞 단계의 입력·성능·안전 결과가 통과해야 다음 단계로 넘어간다.

### 작업 1: 실물 카메라 입력과 네트워크 확인

- 대시보드에서 스트림을 켠 뒤 포트 5000, HTTP 응답 형식, 연결 수 제한, 프레임 크기·속도, 재연결 동작을 실물에서 확인한다.
- 로봇 도메인 15/17과 DDS/WiFi 구조를 확인한다. 카메라 스트림이 DDS와 별도 TCP라면 해당 연결 경로·방화벽도 기록한다.
- PC에서 수신 프레임, 지연, 끊김 후 복구를 관찰한다. 이 단계에서는 로봇 구동 명령을 발행하지 않는다.
- 결과물: 실물 연결 절차, 카메라 규격, 네트워크 측정치, 영상 보관 정책.
- 완료 조건: 각 로봇에서 스트림을 안정적으로 열 수 있고, 연결 종료 후 재접속 동작이 확인된다.

### 작업 2: 관제 launch에 카메라 수신 통합

- 현재는 `pinky_fleet/pinky_fleet/camera_stream.py`가 카메라 TCP 연결과 재연결을 맡는다. 별도 ROS 이미지 토픽을 쓰지 않는다.
- `multi_robot.launch.py`가 로봇별 주소/공통 포트를 전달한다. `start_fleet.sh`는 `ROBOT1_IP`와 `ROBOT2_IP`를 기본 주소로 넘긴다.
- 실행/종료/재시작 및 한 로봇 카메라가 끊겼을 때 다른 로봇과 Nav2가 영향을 받지 않는 구조를 정한다.
- 완료 조건: 기존 fleet 실행 절차로 실행했을 때 영상 수신 구성도 함께 시작되고, fleet 종료 시 관련 프로세스도 정리된다.

### 작업 3: `pinky_fleet` 웹 관제에 영상 표시

- 대시보드에 robot1/robot2별 카메라 패널을 추가한다.
- 현재 선택: 대시보드 HTTP 서버가 `/camera/robot1.mjpg`, `/camera/robot2.mjpg`로 multipart JPEG를 제공한다.
- 영상 상태(연결 중/정상/끊김/오래된 프레임)를 표시하고, 영상 패널이 지도·목표 지정 기능을 가리지 않도록 배치한다.
- 완료 조건: 관제 프로그램 실행 후 별도 YOLO 창을 띄우지 않아도 두 로봇 영상을 구분해 볼 수 있고, 끊김·복구가 화면에 반영된다.

### 작업 4: 인식 파이프라인과 상태 표시

- `pinky_fleet/pinky_fleet/perception.py`에서 패키지의 고정 가중치 `models/yolo11n.pt`로 COCO 모델을 실행하고 오버레이를 표시한다(카메라 입력이 설정된 경우).
- API/UI에 검출 클래스·신뢰도·상자 좌표, 모델 이름, 추론 FPS·지연과 처리 프레임의 지연 상태를 제공한다.
- 프레임 최신성, CPU/GPU 및 WiFi 사용량은 실물 두 스트림 동시 시험에서 측정한다.
- 완료 조건: 동일 물체를 영상 오버레이와 구조화된 인식 결과에서 확인 가능하고, 영상·인식 지연 상태가 구분된다.

### 작업 5: 주행 관련 인식 클래스·데이터셋 확정

- 최종 기능에 필요한 인식 항목을 정의한다: 주행 가능 영역, 차선/경계, 이동 장애물·사람, 횡단보도 등.
- 각 항목의 표현을 정한다(박스 검출/세그멘테이션/상태 분류). 예: 횡단보도 발견 시 감속인지 정지인지 정책 요구도 함께 기록한다.
- 실제 운영 장소·조도·시점 변화를 포함한 데이터를 수집하고 개인정보를 포함한 영상의 보관·공유 규칙을 정한다.
- 학습/검증 영상을 분리하고 클래스별 precision/recall 또는 IoU, 오검출·미검출 사례를 검토한다.
- 모델 파일은 대용량 바이너리이므로 저장소에 커밋하지 않고 별도 배포 경로와 버전·해시를 관리한다.
- 완료 조건: 클래스 정의와 평가 세트, 허용 가능한 미검출/오검출 기준을 주행 정책 담당자와 합의한다.

### 작업 6: 인식 결과를 Nav2 주행 정책에 연결

- 인식 클래스별 동작 표를 만든다. 예: 사람/장애물 전방 검출 → 정지 또는 속도 제한, 횡단보도 접근 → 감속, 차선/주행 영역 이탈 위험 → 목표 추종 속도 제한 또는 일시정지. 각 정책은 거리와 신뢰도 조건, 지속 시간, 복귀 조건을 가진다.
- 2D 검출만으로 거리를 알 수 없으므로, 감지 결과를 라이다 장애물/TF와 공간적으로 연계할지, 카메라는 상황 분류만 맡길지 정한다.
- Nav2와 충돌 없이 적용할 통합 지점을 선택한다. 후보는 (A) Nav2 속도 제한 입력, (B) NavigateToPose 취소/일시정지 후 재개, (C) Nav2 controller 앞뒤의 속도 중재다. 실제 Nav2 버전·구성에서 지원 여부와 효과를 확인하고 하나를 선택한다.
- `cmd_vel` 최종 발행자는 단일화한다. 선택한 통합 지점이 최종 명령 중재를 포함하지 않으면 별도 mux/arbiter와 lease/timeout 동작을 설계한다.
- stale/끊김/저신뢰/인식 노드 오류 때의 동작을 정의한다. 주행 안전에 쓰는 인식 신호를 신뢰할 수 없으면 계속 진행하지 않고 정지 또는 Nav2 기본 안전 주행으로 제한한다.
- 완료 조건: 인식 이벤트 → 정책 결정 → Nav2 영향 → 해제/재개 전 과정이 로그와 관제 UI에서 추적된다.

### 작업 7: 관제 화면에서 주행 인식 상태와 제어권 표시

- 목표 주행 중 현재 인식 경보(예: 사람 감지, 횡단보도, 카메라 stale)와 적용 중인 제한/정지 상태를 표시한다.
- Nav2 목표 상태와 카메라 정책 상태를 구분해 보여준다. 목표 취소와 비상정지를 혼동하지 않게 UI 문구를 설계한다.
- 카메라·인식 실패, 로봇별 도메인 혼선, Nav2/arbiter 상태를 운영자가 확인할 진단 항목을 추가한다.
- 완료 조건: 화면만 보고 로봇이 목표 진행 중인지, 비전 때문에 감속/정지했는지, 센서가 유효한지 구별할 수 있다.

### 작업 8: 통합 검증 및 실물 제한 시험

- 무주행 상태에서 카메라·인식 출력과 상태 고장을 주입해 처리 결과를 확인한다.
- 로봇 바퀴를 띄우거나 구동부를 물리적으로 안전하게 제한한 벤치 시험으로 Nav2와 주행 중재 상호작용을 먼저 확인한다.
- 정지 스위치와 근접 관찰자를 둔 통제된 공간에서 낮은 속도·짧은 목표로 시나리오를 검증한다.
- 정상 경로, 횡단보도/사람 이벤트, 인식 오검출, WiFi 지연, 카메라 단절, 추론 노드 종료, Nav2 실패, 정지 후 복귀 시나리오를 기록한다.
- 최종 통과 조건과 현장 시험은 사람 확인을 받은 뒤 수행한다. 실물 주행 명령을 실행하기 전에는 기존 팀 안전 절차를 따른다.

## 7. 안전·운영 요구사항

- `pinky_bringup`의 속도 명령 타임아웃 부재를 주행 아키텍처의 핵심 위험으로 취급한다. 제어 프로세스 종료 때 0 속도를 자동 발행하는지 보장·검증한다.
- 비상정지는 UI의 Nav2 목표 취소와 분리한다. 기존 문서상 Nav2 취소는 하드웨어 비상정지가 아니다.
- 고정 주행 명령 발행기는 하나로 제한한다. mux/arbiter를 둘 경우 우선순위, lease timeout, 기본 정지 상태, 발행자 죽음 처리까지 명시한다.
- 영상·모델 입력은 관측 가능한 진단 상태를 제공한다. 오래된 인식 결과를 정상 결과처럼 사용하지 않는다.
- `ROS_DOMAIN_ID=15/17`은 로봇별로 별도 프로세스에서 설정한다. 두 로봇 영상이 잘못 섞이지 않도록 UI 카드와 로그에 로봇 식별자를 항상 표시한다.
- 카메라 영상에 사람 얼굴·개인정보가 포함될 수 있으므로 필요한 최소량만 저장하고, 수집 목적·접근 권한·삭제 기준을 정한다.
- 영상, rosbag, 가중치 등 대용량 자료와 IP·비밀번호·토큰을 저장소에 커밋하지 않는다.

## 8. 주요 기술 검토와 결정이 필요한 질문

| 항목 | 현재 판단 | 착수 전 확인 / 결정 |
|---|---|---|
| 카메라 연결 | 대시보드 BLE 제어 HTTP MJPEG `:5000/` 확인 | 로봇 이미지 v1.9 이상인지, 동시 접속 가능 여부, 해상도/FPS와 끊김 후 재접속 확인 |
| AI 실행 위치 | 우선 PC 추론이 현실적 | 관제 PC GPU/CPU 성능, 두 스트림 동시 추론 지연 측정 |
| ROS 영상 인터페이스 | 현재 실물 이미지 토픽 발행은 확인되지 않음 | 카메라 데이터를 ROS로 만들 필요가 있는지, 기존 TCP 입력을 유지할지 선택 |
| 웹 영상 전달 | 대시보드 HTTP multipart JPEG endpoint 구현 | 실물 브라우저 표시와 장시간 연결 안정성은 현장 확인 |
| 도로/횡단보도 모델 | 현재 폴더의 pretrained weights로 해결된다고 볼 수 없음 | 필요한 클래스, 데이터셋, 라벨링 범위, 성능 기준 합의 |
| 장애물 안전 | 기존 라이다/Nav2 중심이 적절 | 카메라 결과를 어디까지 보조 정보로 사용할지 합의 |
| 직접 주행 | 즉시 구현하지 않고 안전 설계 뒤 수행 | Nav2와 모드 전환 방식, cmd_vel 중재, 정지 감시, 현장 승인 절차 결정 |
| 두 로봇 동시 운영 | 도메인 별도 운영 가능 | PC 추론 처리량과 공유기 대역폭을 2대 동시 입력으로 시험 |

## 9. 첫 작업의 완료 조건

최종 완료는 **기존 `pinky_fleet` 관제를 실행하면 각 로봇 영상과 인식 상태가 표시되고, 지도 목표 주행 중 검증된 카메라 인식 정책이 Nav2 주행에 반영되는 것**이다.

현재 코드에서는 작업 2~4의 PC 측 기능(HTTP MJPEG 수신, 웹 표시, 고정 경로 COCO YOLO 오버레이)을 구현했다. 로봇 측 스트림은 Pinky Studio의 카메라 시작 기능과 v1.9 이상 이미지가 필요하며, 실물 연동 확인은 아직 필요하다. 작업 5 이후의 전용 인식 모델·주행 정책과 Nav2 연동은 실제 로봇 영상·클래스 기준·현장 검증이 필요하다. 현재 YOLO 결과는 일반 객체 검출 정보를 보여줄 뿐, 주행 명령에는 연결되지 않는다.

완료 보고에는 다음을 포함한다.

- 로봇별 카메라 연결 방법과 확인된 실제 규격
- 영상 FPS·지연·대역폭 및 연결 복구 결과
- 모델별 PC 추론 FPS·지연과 탐지 예시
- 웹 대시보드 영상 표시 방식
- 도로 요소용 추가 데이터·학습 필요 범위
- Nav2 연동 방식과 `cmd_vel` 단일 발행 구조
- 인식 이벤트별 정책, 정지/감속/재개 조건과 안전 시나리오 통과 결과
